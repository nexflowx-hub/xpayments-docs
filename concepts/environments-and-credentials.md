# Environments & Credentials

XPayments deliberately separates Merchant credentials from provider credentials.

## Credential types

| Credential | Example | Where used | Browser-safe? |
|---|---|---|---|
| Merchant JWT | `eyJ...` | Dashboard / Merchant Platform API | No |
| XPayments TEST key | `xp_test_*` | Payment APIs, server-side | No |
| XPayments LIVE key | `xp_live_*` | Payment APIs, server-side | No |
| Stripe publishable key | `pk_test_*` / `pk_live_*` | Stripe.js / Payment Element | Yes |
| Merchant webhook signing secret | generated by XPayments | Verify XPayments → Merchant | No |
| Provider secret/restricted key | `sk_*` / `rk_*` | XPayments GatewayVault only | No |
| Provider inbound webhook secret | provider-specific | XPayments GatewayVault only | No |

## TEST vs LIVE

TEST and LIVE are strict operational boundaries.

```text
xp_test_* → TEST provider route
xp_live_* → LIVE provider route
```

XPayments should reject incompatible combinations instead of silently sending test traffic to a live gateway or vice versa.

## Server-side API key usage

Bearer form:

```http
Authorization: Bearer xp_live_...
```

Header form:

```http
x-api-key: xp_live_...
```

Stripe-compatible relay additionally accepts Stripe-style HTTP Basic with the XPayments key as username and an empty password.

## Create an API key

Merchant Platform API:

```http
POST /api/v1/api-keys
Authorization: Bearer <merchant-jwt>
Content-Type: application/json
```

```json
{
  "storeId": "<store-uuid>",
  "name": "Production backend",
  "environment": "live",
  "scopes": ["payments_write"]
}
```

The full key is returned when it is created. Save it immediately in the merchant server/hosting secret manager.

## List API keys

```http
GET /api/v1/api-keys
Authorization: Bearer <merchant-jwt>
```

The normal list response exposes metadata/preview, not provider credentials.

## Revoke an API key

```http
DELETE /api/v1/api-keys/{apiKeyId}
Authorization: Bearer <merchant-jwt>
```

Rotate a key by creating a replacement, deploying it to the merchant backend, validating traffic, and only then revoking the old key.

## Stripe Elements configuration

For an authenticated Merchant, the dashboard can obtain Store-specific Stripe Elements compatibility information from:

```http
GET /api/v1/developer/stores/{storeId}/elements-config
Authorization: Bearer <merchant-jwt>
```

When the Store has an active Stripe-compatible route, the response can expose the browser-safe `pk_*` and relay configuration. It must never expose `sk_*`, `rk_*` or provider webhook secrets.

## Secret handling rules

- Never commit real `xp_*`, webhook signing secrets, `sk_*`, `rk_*` or JWTs.
- Never use `NEXT_PUBLIC_` for XPayments server keys or webhook secrets.
- Do not print secrets in CI logs.
- Do not paste real secrets into AI prompts or support tickets.
- Use separate TEST and LIVE environment variables.
- Prefer scoped secrets per Store and per environment.
